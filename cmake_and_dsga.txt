and configure with:

cmake -S . -B build -DCMAKE_PREFIX_PATH=C:\local


That CMAKE_PREFIX_PATH tells find_package where to look for dsga-config.cmake. Once found, dsga::dsga is available and automatically propagates the include path and C++20 requirement to my_target.

Notes:

On find_package — solid. One thing worth knowing: if you have multiple prefix paths, CMAKE_PREFIX_PATH accepts a semicolon-separated list on Windows, e.g. -DCMAKE_PREFIX_PATH="C:\local;C:\other\libs".

On FetchContent — correct. You can also pin to a specific commit hash instead of a tag for tighter reproducibility:

GIT_TAG a1b2c3d4...

On the Unix Makefiles builds — all correct. A couple of additions worth noting:

The -Wno-dev on the GCC line suppresses CMake developer warnings; it's harmless but you may want it on the Clang line too for consistency.

You can pass -DCMAKE_VERBOSE_MAKEFILE=ON when diagnosing build issues to see the full compiler/linker invocations.

To build after configuring: cmake --build build-gcc --config Release (the --config flag is ignored by Makefile generators but harmless to include as a habit).

On --install — correct that the argument must be the build directory. Worth adding: if you omit --config Release on a multi-config generator (like Visual Studio), it defaults to Debug, so the habit of always specifying it is good.

One thing missing from the guide — the CPM approach, since your project decisions doc mentions CPM support. It would look like:

include(CPM.cmake)
CPMAddPackage("gh:davidbrowne/dsga@3.0.0")
target_link_libraries(my_target PRIVATE dsga::dsga)

CPM (CMake Package Manager) is a thin wrapper around FetchContent that adds a few conveniences:

Caching — downloaded packages are stored in a shared cache directory (CPM_SOURCE_CACHE), so if two projects depend on the same library at the same version, it's only downloaded and built once rather than once per project.

Simpler syntax — CPMAddPackage("gh:davidbrowne/dsga@3.0.0") is more concise than the full FetchContent_Declare + FetchContent_MakeAvailable block.

Version deduplication — if multiple dependencies pull in the same package, CPM tries to resolve it to a single version rather than fetching it multiple times.

It's a single-file include — you drop CPM.cmake into your project's cmake/ folder and include() it. There's no install step.

For dsga specifically, since it's header-only and lightweight, the practical difference between FetchContent and CPM is small. CPM starts to shine more when you have several dependencies or when multiple projects on the same machine share the same cache. For your own development and testing of dsga itself, FetchContent is probably fine; CPM is more useful to downstream consumers who have many dependencies.

CPM.cmake is not something you write yourself — it's a third-party project maintained by Lars Melchior at https://github.com/cpm-cmake/CPM.cmake. You just download the latest release of CPM.cmake from there and drop it into your cmake/ folder.

The typical pattern is to either:

Vendor it directly — download CPM.cmake and commit it to your repo at cmake/CPM.cmake, then in your CMakeLists.txt:

include(cmake/CPM.cmake)

Or auto-download it — add this to your CMakeLists.txt and it fetches CPM itself at configure time:

file(
    DOWNLOAD
    https://github.com/cpm-cmake/CPM.cmake/releases/latest/download/CPM.cmake
    ${CMAKE_CURRENT_BINARY_DIR}/cmake/CPM.cmake
)
include(${CMAKE_CURRENT_BINARY_DIR}/cmake/CPM.cmake)

For dsga, since Priority 10 in your roadmap covers package manager support, CPM support is already implicitly handled by the PROJECT_IS_TOP_LEVEL guard in your CMakeLists.txt — a downstream consumer using CPM would just call CPMAddPackage and everything works without any changes needed on the dsga side.
